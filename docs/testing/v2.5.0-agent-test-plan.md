# v2.5.0 test plan for agents — realisation trace, edgy-c4, model 1.10, adapters

**For:** Mistral Vibe, OpenAI Codex, Claude Code, and one person for the
browser, PDF and draw.io checks.

**What:** draft PR #8 (`claude/architecture-diagrams-feature-plan-nz5q57`),
built against the locked plan
[`docs/development-plan-2026-10-v2.5.0.md`](../development-plan-2026-10-v2.5.0.md)
(revision 4). §4a holds its contracts and §8 its acceptance.

**Goal:** prove that the skills *work* (commands, rules, exit codes,
links) and that their *output is good*. Good output means correct EDGY,
correct C4, readable pictures, every link resolving, and honesty about
what is missing.

**Status:** this is the phase 2 draft, written before the code. Commands
use the interfaces the plan specifies. If phase 3 changes a name, the
test plan is updated in the same commit, and §11 of the plan records the
change.

## 0. Rules for every tester

- Use only **fictional** data: Acme Transit, Nordlake Ferries, or a
  company you invent. Never a real client and never a real person.
- Work on a fresh clone of the PR branch, and do not push to it. Report
  in one PR comment per agent, using the template in §9.
- Python 3.8+, and `pip install pyyaml`. Chromium or Chrome is needed for
  P02 only.
- Set:
  ```bash
  R=$PWD
  D=$R/skills/documentation/edgy-diagram
  A=$R/skills/architecture/edgy-assessment
  C=$R/skills/documentation/edgy-c4
  OUT=$(mktemp -d)
  ```
- A test **passes** only when every *Expected* line holds. "Mostly" is a
  fail with a note.
- When you compare bytes, use `EDGY_TEXT_TABLE_ONLY=1`, as the gates do.
- **Pixel review is part of the test.** In v2.4.0, lint reported 0 / 0 on
  pictures that people could not read. Look at the PNG of every page type
  you produce, and say in the report whether you did (§9).

## 3. Track B: realisation trace (F7)

Fixtures live in `$D/examples/` (`trace-map.txt`) and in the test suite.
Build the trace:

```bash
python3 $D/scripts/edgy_generator.py $D/examples/trace-map.txt --output $OUT/trace.drawio --preview --qa
```

**T01 Levels and bands.** Open three pages: a task's, a capability's and
an organisation's.
*Expected:*
- the *above* band holds only lower levels and the *below* band only
  higher levels;
- the *centre* holds the focus and same-level neighbours: for a task, its
  channels; for a process, its assets and people;
- `contains` appears as *part of* / *parts* chips, not as an edge;
- band headers name the levels.

**T02 The link whitelist.**
*Expected:*
- edges only for the links in plan §4 F7, each with its EDGY verb and
  direction;
- `transfers` and other flows are never drawn;
- no `people → process` edge, even when the input has one; the input
  line gives E010 as today;
- a channel page shows its products through *offers*, so no W129 is
  raised for it.

**T03 One hop, deterministic.**
*Expected:*
- a page shows only direct neighbours;
- inside a band, cards are ordered by level, then type, then id;
- generating twice gives byte-identical output.

**T04 Page set and link closure.** Run three ways:
- with `where: CAP-05, APP-07`;
- with `where: from JRN-01`;
- with `where: from JRN-01` and `trace_direction: up`.

*Expected:*
- exactly the specified pages are written;
- every page link in the file points to an existing page (count the
  `data:page/id,` links and resolve them);
- cards without a page are drawn without a link, and `generator_notes[]`
  gives their count;
- the page count is in the notes.

**T05 Algorithm fixtures.** The fixtures are a cycle (two capabilities
requiring each other's assets), a shared dependency (one asset under two
capabilities), a disconnected element and a narrow filter.
*Expected:*
- no infinite loop;
- the shared asset page lists both capabilities above;
- the disconnected element has a page with empty bands and the right
  W129 statuses;
- the narrow filter leaves unlinked cards and counts them.

**T06 W129 and gap keys.** Use the fixture with one empty *below* band
per status.
*Expected:*

| Case | Result |
|------|--------|
| `not_investigated` (the default) or `unknown` | a warning |
| `out_of_scope` or `confirmed_absent` | a note |
| every status | written to `qa.json` `model_gaps[]` with element, band, status and page |
| an organisation page, an `up` page, a same-level link | no W129 |
| a gap key not allowed for the type (for example `gaps: {tasks: …}` on a capability) | E-level in the validator, and a warning in the generator |

**T07 Stable ids.**
*Expected:*
- a trace page id is `trace-<slug>`;
- an id with `/` or `:` gets a six-hex hash suffix;
- renaming an element or reordering the pages leaves the ids unchanged;
- an ordinary page named "Trace CAP-05" gets the `-N` suffix, never the
  trace page's id.

**T08 Page links survive every reader.**
*Expected:*
- `edgy_lint.py`, the native SVG preview and the presenter all see the
  cards wrapped in `UserObject`;
- no card is missing from the lint count, the preview or the presenter's
  element list. Compare the card counts with a run without links.

**T09 Crowded bands.** Use a fixture with 15 neighbours in one band.
*Expected:*
- 11 cards and a "+4 more" card that links to a list page;
- the list page names all 15;
- `generator_notes[]` counts the hidden cards.

**T11 Example gate.** `trace-map.txt` passes

**T12 Direction.**

Install the skills for your agent as a user would (G02, or the Vibe /

**S01 Trace down from a journey** (edgy-diagram 2.9.0; Vibe, Claude).
> "Nordlake Ferries (fictional). The customer journey 'Book a car ferry trip' has the tasks 'find a sailing', 'choose a fare', 'pay' and 'get the ticket', in the app and on the web. The booking product serves these tasks and needs the capabilities 'Trip sales' and 'Payments'. Trip sales is realised by the process 'Sell trips', which needs the booking system and the fare engine; payments needs a payment gateway. The sales team performs 'Sell trips'; IT manages the systems. Show how the journey is realised, so that I can click from the journey down to who does the work."

*Must:*
- write a TXT with explicit ids and `expand: trace`, or trace pages;

*Must not:*
- draw `people → process`;

**S02 Trace up from an organisation** (Vibe, Claude).

*Must not:* raise W129 on upward pages.

**S03 C4 for one application** (edgy-c4 0.1.0; Codex, Claude).

## 8. Track G: output quality (rubric) and Track H: person checks

The rubric has the six criteria of v2.4.0, each scored 0 / 1 / 2: EDGY
correctness, Readability, Completeness, Traceability, Honesty and
Language. For **C4 pages**, *EDGY correctness* reads as **C4
correctness**:
- Person, Software System and Container are used as C4 defines them;
- relationships have descriptions and technologies;
- the boundary is drawn;
- inferred and observed actors are told apart.

A page **passes** with ≥ 10/12 and no 0 (plan §8 Quality). Attach the PNG
of every page that scores below 10.

**Q01 Eval trace.** Claude and Vibe rate independently: the index, two
task pages, two capability pages, an asset page, an organisation page
and a list page from T10. Report every criterion on which the two raters
differ by 2 points.

**Q02 C4 pages.** Rate L1 for three eval applications: one with an
observed Person, one with only inferred Persons, one with no Person.
Rate L2 of the fare engine.

**Q03 Agent outputs.** Rate the maps of S01–S03, S05 and S06 per agent,
and compare runs of the same prompt.

**Q04 Slide test.** Show one trace path (journey → organisation) and one
C4 L1 to an architect. *Would you put this on a slide without editing?*
Answer yes, with edits (list them), or no (say why).

**H01 draw.io desktop.** Open `eval.drawio` and `c4.drawio` in draw.io
desktop.
*Expected:*
- the page links work: a click on a linked card opens the page;
- the C4 pages render with their styles;
- nothing is reported broken.

**H02 PDF.** Export `eval.drawio` to PDF from draw.io.
*Expected:* the page links survive as internal PDF links, as plan §4 F7
requires.
