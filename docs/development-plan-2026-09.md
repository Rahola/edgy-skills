# EDGY skills development plan (2026-09, revision 2)

**Revision 2 (2026-09-27)** merges two sources:

- **Review A — cross-session diagram review.** Retrospective, programmatic and
  visual analysis of EDGY diagrams and reports produced by agents in earlier
  sessions (assessment deliveries, reframings, experiments).
- **Review B — field feedback from an enterprise-architecture programme.**
  Written feedback from a team that used the skills for real target-state
  architecture work in a public-sector organisation: about 15 EDGY-notation
  diagrams (multi-page draw.io + PNG) plus wiki pages, over several weeks. The
  team ended up building its own generator, renderer and validator because
  the skills did not cover nesting, multi-page files, routing at scale,
  CLI-free preview or transition marking. Their feedback was written against
  edgy-assessment 1.1 / edgy-diagram 1.3 / edgy-framework 1.2; this plan
  states for each item whether the current versions (1.5 / 1.7 / 1.2) already
  resolve it.

The plan states *what* needs to improve, *why*, and — new in revision 2 —
*what belongs in this repository and what does not*.

> 🔒 Both sources originate from private work. Deliveries are referred to only
> by labels and aggregate numbers. No client or organisation names, no
> business content (see the privacy rule in `AGENT_LOG.md`).

## 2. Key findings

### 2.1 Two parallel generation paths produce different quality (A)

`edgy-diagram/SKILL.md` instructs: *"Generate draw.io XML directly — DO NOT
use Python scripts."* At the same time the repo ships a 1,266-line
`edgy_parser.py` with 30 tests. Comparison on the same inputs:

| Metric (files with the problem) | Hand-written XML (n=20) | Parser (n=24) |
|---------------------------------|------------------------:|--------------:|
| Legend missing (SKILL.md: *mandatory*) | **16** | 0 |
| Negative coordinates | **7** | 0 |
| Elements outside the page | **6** | 0 |
| Text does not fit the element | **15** (121/287 elements) | 8 (41/479) |
| Overlapping elements | 0 | **3** |
| Edges with exit/entry anchors | 0/20 | 24/24 |
| Core-link verb on a wrong element pair | 4 | 5 |
| Non-core link drawn with core-link style | **8** | 0 |

7 of 20 delivered diagrams were saved with draw.io desktop, and autosave
backups show a human moved 4–20 elements per diagram after generation.
Review B reaches the same conclusion from the other direction: a 75-cell
capability map is "practically impossible to keep correct" as hand-written
XML, and 60 lines of Python made it repeatable.

**Conclusion:** the right division of labour is
**LLM → semantic model → deterministic layout → lint → preview**. The LLM
should not place pixel coordinates.

### 2.2 Link semantics leak (A, confirmed by B)

- Core-link verbs used on non-core pairs (4 hand-written, 5 parsed diagrams).
- Free influence verbs drawn with the solid core-link arrow in 8 diagrams;
  no vocabulary of accepted influence verbs.
- Review B hit the same gap from the modelling side: there is no official
  capability → purpose link, so the team bridged through an Outcome base
  element and asked for the rule *"when no core link fits, use Influence
  with a verb — do not invent a new Link"*.
- `facet: all-facets` (typo) silently fell back to `identity`; the parser
  records a warning but `edgy_generator.py` never prints it.
- The core-link table is copied into four SKILL.md files.

### 2.3 Visual quality and structure fall short of real maps (A + B)

Review A compared deliveries with the official maps; Review B lists what
real architecture work needed. They agree:

| Feature | Official maps / field need | Skill today |
|---------|----------------------------|-------------|
| Containers, lanes, nesting (`container=1`, `parent`, relative geometry) | required for capability areas, layers, role lanes | SKILL.md says only "all cells directly under root" |
| Multi-page `mxfile` with named pages | required (metamodel + example + table in one file) | bare `mxGraphModel` only |
| Name + subtext (ids, page refs, current implementer) | required | `"Name - Description"` rendered as one bold string; tags/metrics get a subtext, the description does not |
| Element ids (`PUR-01`, `ADR-004`) for cross-references | required | no `id:` field |
| Routing above ~10 elements: sides, waypoints, channels, anchors | required | anchors exist in the parser (1.7); no waypoints, channels or anchors in the input format |
| Intersection elements *between* the facets | official maps; B: "Org/Brand in the top row of the purpose map, not the bottom" | placed at the bottom → edges cross the whole canvas |
| Current → target transition marking | central to target-state work | none (metric colours express *rating*, not *change*) |
| Label conventions | one rule | three conventions in the wild |

### 2.4 Rendering does not work in agent environments (A + B, high)

The draw.io CLI was missing in every reviewed session and could not be
installed in the programme's sandbox. Both reviews conclude that a preview
image is not optional: every first version in Review B had overlaps, cut
text or spaghetti routing that only became visible in the PNG. The PlantUML
path exists but is not wired into the assessment workflow.

### 2.5 Weaker models fail the skill completely (A)

An issue log in the upstream repo documents a session that produced empty
files, `mxfile` wrappers with `mxStyle` children and finally XML with
`mxCell` elements **nested** under `id="1"` — the structure SKILL.md forbids —
without the agent noticing. Review B points out that the log's "final" XML
still teaches that wrong structure. There is no executable check beyond the
byte count.

### 2.6 Modelling guidance is missing where it matters most (B)

- **Strategy → EDGY.** A first version modelled strategic focus areas as
  Story. The architect corrected: mission and vision are top-level Purposes,
  focus areas are sub-Purposes (purpose map), KPIs are Outcome base
  elements, initiatives are Activities with exactly one Outcome each. The
  framework skill says nothing about this.
- **Capability formulation.** The framework asks only "what capabilities are
  needed". The programme's most important learning was that the capability
  map is the *stable* home of requirements and a coverage checklist, not the
  unit of work; one system spanning several capabilities is normal; two
  systems on one capability without a master decision is the problem. Eight
  helper questions and a granularity rule (level 1 = 6–12 areas, level 2 =
  40–80 capabilities) emerged and should be taught by the skill.
- **Outcome is missing** from the 12-element list in the reframing matrix, so
  KPIs went unmodelled at first. Finnish names for the base elements are
  also missing.
- **Organisation intersection.** "How do we organise as teams?" was too
  generic; the useful question was *who steers, procures, defines, produces,
  operates and approves each block, and where is one small team on three
  work packages at once*.

### 2.7 The assessment skill is the wrong mould for internal target-state work (B)

The assessment assumes an external target company, public sources, 9 files,
150-line minimum and all 12 elements. Internal architecture work had
different inputs (strategy PDF/xlsx, meeting transcripts, an existing
ArchiMate current state, wiki workspace, interviews) and different outputs
(purpose map, capability map + cards, guardrails, building-block hypothesis,
work packages, decision log, governance model, stakeholder summary). The
Experience facet was not central at that stage; forcing it would have been
waste. Length minimums were harmful: stakeholders needed a one-paragraph
summary with one picture, not 150 lines.

### 2.8 Assessment outputs have drifted; documentation is oversized (A)

3/6 reports predate the locked PDF preamble; 0/6 deliveries contain
`edgy-model.json`, so `edgy-deep-dive` cannot run on any existing client;
section 10 (suggested deep-dives) is missing from all six.
`edgy-diagram/SKILL.md` is 978 lines; the legend XML and palette are
duplicated in `edgy-assessment`.

### 2.9 Feedback items already resolved in current versions

| Review B item | Status in edgy-diagram 1.7 |
|---------------|----------------------------|
| Influence and Tree look the same | **Resolved**: Influence = `dashed=1;endArrow=open`, Tree = solid, no arrowhead |
| "orthogonalEdgeStyle alone" | **Partly**: the parser emits distributed exit/entry anchors; waypoints and channels are still missing |
| Legend | **Resolved in the parser**, still missing in hand-written output |
| Dynamic element width | **Resolved in the parser** (min 120 / max 280 by text length) |
| Tags/metrics as subtext | **Resolved**; the `- Description` part is not |

## 3. Scope decisions: what belongs in this repository

Guiding principle: this repository packages **EDGY notation, EDGY-based
modelling guidance, and agent-agnostic tooling with standard-library
dependencies**. It does not package an organisation's delivery channels,
project-management artefacts that are not anchored in EDGY elements, or hard
dependencies on tools an agent sandbox may lack.

| Feedback item | Decision | Rationale |
|---------------|----------|-----------|
| CLI-free SVG/PNG preview + mandatory "look at it" loop | **In** (P0) | Notation-level tooling; every agent environment needs it |
| `mxfile` wrapper, multi-page `pages:` | **In** (P0) | Format correctness; needed by any draw.io consumer |
| Containers, lanes, nesting; `group:` / `lane:` | **In** (P1) | Official EDGY maps are built from containers |
| Title + subtext labels, size classes, `id:` field | **In** (P1) | Notation-level; ids are generic cross-reference keys |
| Routing by size class; `from:` / `to:` / `via:`; channels; invisible anchors; bus pattern | **In** (P1), patterns documented in a reference file | Generic draw.io technique in service of EDGY diagrams |
| Transition overlay `{change: keep\|change\|replace\|new\|remove\|decide}` | **In as a clearly labelled EDGY extension** (P1), off by default | Not part of EDGY 23; fill stays the facet colour, only the stroke carries change. Widely needed in target-state work |
| Map-type layout rules (capability areas, purpose hierarchy with Outcomes and Org/Brand on top, organisation as role model) | **In** (P1) | These are EDGY map types |
| `reference` layout (layered reference architecture with lanes) | **In as an extension layout** (P2) | Uses EDGY elements in lanes; generic enough |
| `summary` layout (stakeholder picture, 3–4 boxes) | **In as a lightweight preset** (P2) | Small; the programme's most effective picture. Kept generic (Organisation / Process / Outcome rows) |
| `validate_drawio.py` | **In** — merged into `edgy_lint.py` (P0) | Same tool; Review B adds empty-container and absolute-position checks |
| Strategy → EDGY mapping table + "focus areas are not Story" anti-pattern | **In** (P1, edgy-framework) | EDGY modelling guidance |
| Capability formulation questions, three uses, granularity rule | **In** (P1, edgy-framework) | EDGY modelling guidance; also condensed into the capability map instructions |
| Outcome row in the reframing matrix; Outcome verbs (`produces`, `measures` as Influence); Finnish base-element vocabulary | **In** (P1) | Notation completeness |
| Organisation role-model check (steer / procure / define / produce / operate / approve) | **In** (P2) | Grounded in `organisation → process: performs` |
| Load heat map per team per phase with a threshold | **Partly** — an optional view in the role model, no threshold semantics | Resource management, not EDGY; keep as a documented option only |
| Length requirements by mode; "do not pad" anti-pattern | **In** (P2) | Fixes a harmful rule in the skills |
| `mode: target-state` in edgy-framework and an `edgy-target-state` orchestrating skill | **In, scoped** (P2) | EDGY-anchored artefacts only: purpose map, capability map + cards, building-block hypothesis mapped to capabilities and Outcomes, role model, summary picture |
| Guardrails, work packages with procurement alternatives (A–D), decision log (ADR) | **Partly** — thin templates that reference Purpose/Outcome/Capability; ADR generation delegated to the maintainer's existing ADR skill via an optional hook | Generic EA / programme-management content; not EDGY notation. The repo should not grow a second ADR skill |
| Confluence page structure, lozenges, smart links, Atlassian MCP delivery, version clean-up | **Out** | Organisation- and tool-specific delivery. Belongs in the organisation's own skill set. The repo keeps a one-paragraph generic delivery note (one `.drawio` with all pages + one PNG per page, naming convention) |
| Meeting-transcript (VTT) processing into decisions and ADR candidates | **Out** | A separate meeting-minutes skill already exists upstream; the target-state workflow only *references* it as an optional input step |
| `layout_from: file.archimate#view` positioning | **In, low priority** (P3), standard-library XML parsing only, no Archi dependency | Small, genuinely useful for "same place = same responsibility"; must not depend on the ArchiMate MCP skill |
| Fix or remove the issue log that teaches nested `mxCell` | **Out of this repo** (the log lives upstream, `generated/` was pruned here); noted for the upstream maintainer | — |
| Playwright as a dependency | **Out** — use headless Chromium/Chrome if present on PATH, else deliver SVG only | Keep tooling standard-library; Playwright is an environment choice, not a skill requirement |
| The team's `edgylib.py` | **Reference only** — port ideas (multi-page writer, lane/anchor helpers, SVG renderer), not code carrying project content | Privacy; the repo's tooling must be self-contained and Apache-2.0 |

## 4. Target state

1. **One generation path:** semantic model (TXT/JSON) → deterministic
   generator → lint → preview. The LLM does not place pixel coordinates;
   direct XML is a fallback for < 15 cells, and even then lint is mandatory.
2. **The format scales to real architecture work:** multi-page files,
   containers and lanes, name + subtext + id, routing rules by size,
   a transition overlay for current → target views.
3. **Diagrams look like EDGY 23 maps:** containers, intersection elements
   between the facets, short and correctly styled core links.
4. **The pipeline runs without a human and without draw.io desktop:**
   SVG/PNG produced in Python (plus headless Chromium when present) or via
   PlantUML.
5. **The framework skill teaches the modelling decisions that went wrong in
   the field:** strategy → EDGY, capability formulation, Outcome, role model.
6. **A target-state workflow exists** for internal architecture work, scoped
   to EDGY-anchored artefacts, next to the external assessment.
7. **One source of truth for core links** and no duplicated instruction blocks.

## 8. Risks and scope limits

- **Breaking change (P0.2):** the parser must cover what agents did by hand
  (titles, containers, pairwise) before the default flips; pairwise layout
  goes into the parser before `edgy-deep-dive` moves off direct XML.
- **Relative geometry (P1.1)** changes lint and renderer maths; ship P0.1
  with parent-chain support from the start.
- **Extensions vs. notation:** the transition overlay, `reference` and
  `summary` layouts are labelled as EDGY *extensions* in every place they
  appear, so users do not mistake them for EDGY 23 notation.
- **Target-state scope creep:** guardrails, work packages and decision logs
  stay thin and EDGY-referencing; ADRs, meeting minutes and wiki delivery are
  delegated to other skills. If a future request needs more, it belongs in
  the organisation's own skill set, not here.
- **Tool dependencies:** the only hard dependency stays Python 3 standard
  library. Headless Chromium, PlantUML and the draw.io CLI are detected, never
  required.
- **Privacy:** the eval set uses fictional companies; lint runs on real
  deliveries happen in private repos; only aggregates are recorded here.
