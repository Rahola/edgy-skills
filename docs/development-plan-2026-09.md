# EDGY skills development plan (2026-09)

This plan is based on a **retrospective review of EDGY diagrams and reports
produced across several earlier agent sessions**. The material was analysed
programmatically (shapes, colours, layout, link semantics) and visually
(rendered and compared against the official EDGY 23 example maps). The plan
states *what* needs to improve in the skills and *why*. It does not reproduce
the content of any individual delivery.

> 🔒 The reviewed material originates from private engagements. This document
> refers to deliveries only by the labels **A–F** and by aggregate numbers.
> No client names, no business content (see the privacy rule in
> `AGENT_LOG.md`).

## 2. Key findings

### 2.1 Two parallel generation paths produce different quality

`edgy-diagram/SKILL.md` instructs: *"Generate draw.io XML directly — DO NOT
use Python scripts."* At the same time the repo ships a 1,266-line
`edgy_parser.py` with 30 tests (collision resolution, dynamic width, legend,
edge anchors). Comparison on the same inputs:

| Metric (files with the problem) | Hand-written XML (n=20) | Parser (n=24) |
|---------------------------------|------------------------:|--------------:|
| Legend missing (SKILL.md: *mandatory*) | **16** | 0 |
| Negative coordinates | **7** | 0 |
| Elements outside the page | **6** | 0 |
| Text does not fit the element¹ | **15** (121/287 elements) | 8 (41/479) |
| Overlapping elements | 0 | **3** |
| Edges with exit/entry anchors | 0/20 | 24/24 |
| Core-link verb on a wrong element pair | 4 | 5² |
| Non-core link drawn with core-link style | **8** | 0 |

¹ Heuristic: text length vs. box area. Hand-written diagrams used fixed
120×60 / 140×60 boxes although name + description ran to 60–120 characters.
² The parser validates direction only, not the pair, so the same input error
passes through.

**In addition:** 7 of 20 delivered diagrams were saved with draw.io desktop
(`<mxfile host="Electron">`), and the autosave backups show that a human
moved 4–20 elements per diagram by hand after generation. A manual fix-up
round has therefore been part of every delivery.

**Conclusion:** XML written directly by the LLM regularly violates exactly
the rules SKILL.md lists under "CRITICAL" (legend, coordinates, text fit).
The parser enforces them mechanically, but its layout is dull and places the
intersection elements far from their facets. The current "write the XML
directly" default is wrong; the right division of labour is
**LLM → semantic model → deterministic layout → lint**.

### 2.2 Link semantics leak

- Core-link verbs (`requires`, `realises`, `pursues` …) were used on pairs
  that are not among the 24 official EDGY 23 core links (4 hand-written
  diagrams, 5 parsed; same input → same error).
- Free influence verbs (`enables`, `guides`, `does`, `offers`, `manages`,
  `reflects`) were drawn with the solid core-link arrow in 8 diagrams. The
  skill has no vocabulary of accepted influence verbs, so the agent invents
  them every time.
- In one delivery non-ASCII letters were double-escaped (`&amp;auml;`), so a
  core-link verb renders correctly but is not machine-recognisable.
- An input with `facet: all-facets` (typo) silently fell back to the
  `identity` default. The parser records a warning in `warnings`, but
  **`edgy_generator.py` never prints it**.
- The core-link table is copied into four SKILL.md files (4 × 24 rows). They
  are in sync today, but every change has to be made four times.

### 2.3 Visual quality is far from the official maps

The official EDGY 23 maps (`examples/official/`) are **layout-only** in 11
of 16 cases: meaning comes from coloured group containers and three-level
nesting, not from arrows. The delivered diagrams are the opposite: 5–24
elements and 8–20 long edges crossing the whole canvas, with no containers.

| Feature | Official maps | Delivered diagrams |
|---------|---------------|--------------------|
| Facet containers / column headers | always | 4/20 (added by hand) |
| Leaf element size | 130×60, font 14 | 120×60, font 12, text overflows |
| Name vs. description | name only in the box | `"Name - Description [tags] {metrics}"` in one label |
| Edges | few, short, T-branched | many, long, crossing, labels on top of shapes |
| Intersection elements | *between* the facets | at the bottom → 20 edges across the canvas |

Label conventions vary by delivery: `"Name - Description"`, `"Type Name"`,
`"Name | tags"`. There is no single rule.

### 2.4 Rendering does not work in agent environments

The draw.io CLI was missing in every reviewed session (including this one).
PNG exports succeeded in only one delivery (on a human's machine). The
`edgy-assessment` "PDF Report Generation" phase requires PNG diagrams via
`--preset presentation`, so the PDF pipeline is de facto broken without a
human. The PlantUML path (`<edgy/edgy>` stdlib) is implemented but not wired
into the assessment workflow.

### 2.5 Weaker models fail the skill completely

`generated/AGENT_LOG_EDGY_DIAGRAM_ISSUE.md` documents a Mistral Vibe session
that produced (a) empty 324-byte files, (b) an `mxfile` wrapper with
`mxStyle` children, and (c) finally XML with `mxCell` elements **nested**
under the `id="1"` cell — exactly the structure SKILL.md forbids — without
the agent recognising the error after ten attempts. Two deliveries (A, B)
had to be regenerated from scratch with Claude Code.

The skill relies on the agent *reading* and *following* 978 lines of
instructions. There is no executable check that tells the agent "this file is
broken", other than the byte count from `ls -la`.

### 2.6 Assessment outputs have drifted over time

- 3/6 reports have no PDF preamble (made before the locked layout of
  v1.3.0); 3/6 have it. Old reports cannot be run through the new pipeline.
- **0/6** deliveries contain `edgy-model.json`, so `edgy-deep-dive` cannot
  be used for any existing client.
- Report length ranges from 164 to 391 lines; all share the same 9-section
  skeleton (good), but section 10 (suggested deep-dives) is missing from
  all of them.
- The reframing reports (2) follow the `edgy-framework` template well; one
  added an extra "Strategic choices" section — the template could offer an
  optional slot for it.

### 2.7 Documentation size and duplication

`edgy-diagram/SKILL.md` is 978 lines (the earlier target was < 500). The
legend XML (17 cells) is copied verbatim into both `edgy-diagram` and
`edgy-assessment`. The same applies to the colour palette and shape rules.
Three of the four documents say "generate the XML directly" and one says
"use the parser" — the agent receives a contradictory signal.

---

## 3. Target state

1. **One generation path:** the agent produces a *semantic model*
   (TXT/JSON), a deterministic tool produces the XML, and a linter rejects
   invalid files before delivery. The LLM no longer places pixel coordinates.
2. **Diagrams look like EDGY 23 maps:** facet containers, name separated
   from description, intersection elements between the facets, core links
   short and correctly styled.
3. **The whole pipeline runs without a human and without draw.io desktop**
   (SVG/PNG produced in Python or via PlantUML).
4. **A single source of truth for core links** — vocabulary in one file, from
   which tables and validation are derived.
5. **Existing deliveries can be lifted to the new level** without
   re-analysis (model extraction + regeneration).

---

## 4. Actions

Priorities: **P0** = fixes a recurring quality defect, **P1** = raises the
output to the level of the official maps, **P2** = extends usability,
**P3** = clean-up.

## 7. Risks and scope limits

- **Breaking change (P0.2):** flipping the default path requires the parser
  to cover every case agents have so far handled by hand (titles,
  containers, pairwise). Add the pairwise layout to the parser before moving
  `edgy-deep-dive` off direct XML.
- **Container `parent` references** make coordinates relative; the linter
  and the SVG renderer must account for this (P0.1 before P1.1).
- **The official maps are layout-only**; our facet diagrams still need the
  core links. Compromise: containers + only core links visible, influence
  links hidden by default (`--show-influence` shows them).
- **Privacy:** the eval set (P3.3) uses fictional companies; lint runs
  against real deliveries happen only in the private repo, and only
  aggregates are recorded in the public log.
- This plan does not cover the `archimate` or `c4` skills, which have their
  own EDGY mappings upstream; aligning them with the core-link vocabulary
  (P0.6) is separate work.
